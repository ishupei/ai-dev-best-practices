# 综合检查与落地评审

用于独立判断需求、方案、设计、代码改动、任务结果或回答内容是否符合已标定依据，以及是否具备继续设计、拆解、实现或验收的条件。

核心原则：**标定优先，证据其次，验证最后**。测试、回滚和命令输出只作为支撑评审结论的证据，**MUST NOT** 将本技能扩展成完整测试设计、测试用例生成或发布审计。

默认行为：只检查和建议。除非用户明确要求“修复、更新、回写、补充、改掉”，否则 **MUST NOT** 修改代码或文档。

## 输入选择

- 如果用户指定了内容、文件、目录、commit、diff、PR 或检查重点，优先检查用户指定对象。
- 否则检查当前对话中最近的相关回答、方案、设计、任务输出或代码变更摘要。
- 否则在存在 Git 工作区改动时检查当前 `git diff`。
- 否则检查工作空间根目录 `docs/` 下最新且相关的 `DRAFT/PLAN/DESIGN/TASK/SUMMARY`。
- 如果没有可靠检查对象，要求用户提供检查目标，**MUST NOT** 凭空评审。

`docs/` 一律指当前工作空间根目录下的 `docs/`。多模块仓库中，**MUST NOT** 默认读取子模块、子工程、包、服务或组件目录下的 `docs/`。如果用户指定的路径不在工作空间根目录 `docs/` 内，先说明路径风险并获得确认。

## 标定依据

按下列优先级识别有效标定依据：

1. 用户指定材料或用户明确确认。
2. 同一功能目录下的 `DRAFT/PLAN/DESIGN/TASK/SUMMARY`。
3. 接口契约、现有代码、Git diff、配置、数据结构、命令输出。
4. 有明确来源的对话上下文。

如果没有标定依据支撑结论，标注为 `信息不足` 或 `待确认`；**MUST NOT** 将通用最佳实践写成项目事实。

## 检查维度

- 需求/方案/设计：标定符合度、需求覆盖、架构边界、数据/API 契约、兼容性、依赖前提、验收口径、实施路径。
- 代码：需求/设计/任务符合度、正确性、边界条件、异常处理、数据一致性、并发/幂等、安全、性能、可维护性、已有验证证据。
- 回答/内容：事实依据、逻辑链条、术语准确性、结论强度、前提限制、误导风险。
- 综合上下文：标定依据一致性、任务衔接、未决问题、依赖条件、下一步可执行性。

仅当对象涉及上线执行、数据迁移、兼容性风险或高影响代码改动时检查回滚方案；其他场景如需提及，标注为 `不适用` 并说明原因。

## 确认状态

关键需求、功能点、决策、验收标准或任务项只能使用以下状态：

| 状态 | 使用条件 | 处理要求 |
|------|----------|----------|
| `已确认` | 有标定依据或证据直接支持 | 可继续推进；必要时建议回写 |
| `待确认` | 缺少规则、边界、数据含义、权限、兼容性、验收口径或依赖前提 | 列出确认问题和建议默认值 |
| `有争议` | 输入来源冲突，或多种解释会实质影响交付 | 列出冲突来源、影响和推荐裁决方式 |
| `不适用` | 当前检查维度与对象无关 | 简述不适用原因 |

需求、方案、设计检查必须输出功能点或关键结论确认表。代码检查应尽量映射到对应需求、设计或任务；无法映射时标注 `待确认` 或 `不适用`。

## 工作流程

1. 锁定检查对象：说明对象类型、实际读取的输入、未覆盖范围。
2. 建立标定依据：列出使用的文档、代码路径、diff、命令输出或用户陈述。
3. 对照标定检查：识别已对齐点、缺失点、冲突点、过度确定表述和不可执行假设。
4. 分类问题：真实缺陷或交付风险进入 Findings；风格或可选优化进入 Suggestions。
5. 评分并输出：使用下方输出契约；只有低成本且与结论直接相关时才执行验证命令。

代码检查优先读取 `git diff` 和附近调用链。只有验证成本低且能增强结论可信度时才运行测试或命令；未运行时说明原因。

## 评分规则

总分 `10` 分，默认分项：

- 标定符合度：`2`
- 准确性：`2`
- 完整性：`2`
- 可落地性：`2`
- 风险控制 / 清晰度 / 可维护性：`2`

证据约束：

- 证据不足时，总分最高 `6/10`。
- 关键输入缺失时，总体结论必须为 `信息不足`。
- `待确认` 和 `有争议` 项必须体现在完整性、可落地性或风险控制扣分中。

评分尺度：

- `9-10`：基本可直接推进，仅有轻微表达或证据补充建议。
- `7-8.5`：方向正确，可推进，但存在非阻塞遗漏或有限验证缺口。
- `5-6.5`：存在明显缺口，需修改后再推进。
- `3-4.5`：关键逻辑、实现或表达存在高风险问题。
- `0-2.5`：结论不可采信、方案不可落地或存在阻塞性缺陷。

## 回写策略

默认只输出回写建议。

只有用户明确要求“回写、更新、补充、修复、修改文档”时才写文件，并且写入同一工作空间根目录下的功能目录：

- DRAFT：需求范围、功能点、业务规则、验收口径、仍待澄清事项。
- PLAN：技术路线、架构边界、API/数据模型、兼容策略、风险、必要验证。
- DESIGN：关键决策、详细流程、异常处理、安全/性能约束、待确认设计问题。
- TASK：任务拆解、依赖关系、验证方式、阻塞项、进度状态。
- SUMMARY：已确认结论、未决问题、当前进度、下一步。

不得将被否定选项、提问过程、临时推理或无依据扩展写入文档。无法唯一确定目标文档时，先询问用户，**MUST NOT** 猜测覆盖。

## 输出契约

每次检查优先输出以下结构。对象很小时可以压缩，但不得省略评分、本轮对齐点、修改方向和验证记录。

通过 / 有条件通过 / 不通过 / 信息不足。简述判断。

**评分**
X/10
- 标定符合度：x/2，理由。
- 准确性：x/2，理由。
- 完整性：x/2，理由。
- 可落地性：x/2，理由。
- 风险控制/清晰度/可维护性：x/2，理由。
- 主要扣分点：...
- 最大风险：...

**本轮对齐点**
- ...

**功能点/关键结论确认表**
| 条目 | 状态 | 依据 | 风险 | 下一步 |
|------|------|------|------|--------|
| ... | 已确认/待确认/有争议/不适用 | ... | ... | ... |

**Findings**
- P0/P1/P2/P3：问题。依据：... 影响：... 建议：... 验证：...

**遗漏与待确认**

- 建议回写文档：...

## 完成自检

- 检查对象、输入来源和未覆盖范围已说明。
- 每个结论都有依据；不确定项已标注。
- 关键条目已使用四类确认状态，或说明 `不适用` 原因。
- Findings 与 Suggestions 已区分。
- 评分使用五项分值，并反映待确认/有争议项。
- 产生确认结果变化时已给出回写建议；未获用户明确要求时未修改文件。
- 验证记录已说明检查了什么、执行了什么、未执行什么。
